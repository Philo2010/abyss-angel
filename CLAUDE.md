## Project Overview

Abyss-Angel is a **FIRST Robotics scouting platform** — a Rocket (Rust) web server for collecting, managing, and analyzing match and pit scouting data from FIRST Robotics competitions. It integrates with The Blue Alliance (TBA) API and targets the 2025/2026 seasons.

## Commands

```bash
cargo build              # Debug build
cargo build --release    # Release build
cargo run                # Run the server
cargo clippy             # Lint
cargo fmt                # Format
```

No automated test suite exists. The server starts on `0.0.0.0` and auto-syncs SeaORM schema on startup.

**Database:** Requires PostgreSQL. Connection string is set in both `.env` and hardcoded in `src/main.rs` (`Settings::db_path`). The local DB is `postgres://philipbedrosian@localhost/testdb`.

**TBA API key** is also hardcoded in `src/main.rs` under `Settings::blue_api_key`.

## Architecture

### Request Flow

```
HTTP request → Rocket route (src/frontend/) → Module logic (src/snowgrave/, src/pit/, etc.) → SeaORM (src/entity/) → PostgreSQL
```

All endpoints return `ApiResult<T>` (a wrapper with `status` and `message` fields). Auth is cookie-based (UUID session cookies).

### Key Modules

- **`src/auth/`** — Login, user creation, bcrypt hashing (cost 12), cookie sessions, admin checks
- **`src/frontend/`** — All Rocket route handlers, organized by feature (snowgrave, pit, graph, averages, search, scoutwarn, etc.)
- **`src/snowgrave/`** — Core match scouting logic: TBA integration (`blue.rs`), match queuing, scout assignment, validation (`check_system/`), MVP data insertion
- **`src/pit/`** — Pit scouting system; uses a `PitScoutStandard` trait with year-specific implementations (e.g., `pit_2025`)
- **`src/entity/`** — SeaORM-generated DB models for all tables (`user`, `upcoming_game`, `game_scouts`, `mvp_data`, `warning`, `pit_header`, `dyn_settings`, etc.)
- **`src/backenddb/`** — Game data models and conversion from DB rows to Snowgrave domain models
- **`src/setting/`** — Dynamic event configuration via `dyn_settings` table (get/set current event code)

### Scouting Data Flow

1. Pull matches from TBA → `upcoming_game` table (`/api/snowgrave/queue_match`)
2. Assign scouts → `game_scouts` table (`/api/snowgrave/scout_insert` / `scout_edit`)
3. Submit scouted data → `scout_game_midway_insert` table
4. Validate via `check_system/` (bind, mid, precheck, filled checks)
5. Convert via `backenddb/` to domain model, store final data
6. Query via `/api/averages`, `/api/graph`, `/api/search`, `/api/snowgrave/get_leaderboard`

### Game Model Macro

The `game!` macro (see `hehe.rs` and `src/backenddb/`) generates game-specific data structures and serialization. Year-specific game models live in `src/backenddb/`.

### OpenAPI

`schima.json` in the project root is a generated OpenAPI 3.0 spec. It's regenerated by the server (via `rocket_okapi`) and documents all ~30 endpoints.
